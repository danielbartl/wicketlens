# Custom inputs and composite markup

The extended source-analysis slice supports custom inputs derived from
`FormComponent<T>`, and composite inputs derived from `FormComponentPanel<T>`.
Panels embedding these inputs use the same constructor and scope rules.

## Two different markup scopes

```java
Form<Void> form = new Form<>("form");
form.add(new CustomInput("name"), new CompositeInput("editor"));
add(form);
```

The page report pairs `form`, `form:name`, and `form:editor` against the page's
HTML. A plain `FormComponent` uses that owner markup; WicketLens does not invent
a companion HTML scope for it.

`FormComponentPanel` extends `FormComponent`, rather than `Panel`, but owns
`<wicket:panel>` markup. Opening `CompositeInput.java` or its unique conventional
`CompositeInput.html` companion analyzes the internal fields separately. The
outer `editor` ID continues to navigate to its tag in the page HTML. Root **Go to
HTML** opens the composite's companion. Source/markup inheritance, editor
following, ID references, completion, paired rename, inspections, and orange ID
coloring use the existing analysis pipeline in each scope.

For a matched `Panel` or `FormComponentPanel`, valid preview descendants inside
the parent tag are inactive. They produce no missing-pair inspection. Malformed
HTML and document-wide uncertainty are retained. Children explicitly added to a
composite by its caller remain unresolved in the caller report: pairing them
requires the composite's separate markup and construction context. Internal
nodes are never flattened into the parent's markup graph.

## Constructor and conversion contract

ID tracing follows source `super(...)`/`this(...)` delegation to reviewed Wicket
constructors, retaining reordered arguments and fixed literals. The Wicket
10.11.0 source audit adds both public overloads of `FormComponent` and
`FormComponentPanel`. Each forwards its unchanged ID through
`LabeledWebMarkupContainer` to `Component`'s final ID storage.

Custom form components and Panels may additionally contain bounded, isolated
setup: literal scalar fields, private final input fields, direct `add(...)`
calls with supported fresh inputs or those fields, a single constructor
assignment to a private final field, and a leading `super.onInitialize()` followed
by such additions. The constructor proof requires child creation arguments to
be literals. Final local components and additions to owned final local/field
containers are supported too, including setup generated by inspection fixes.
The proof does not execute helper calls or model-building expressions.
Literal/class-literal `setRequired(...)` and `setType(...)` calls resolve to the
reviewed `FormComponent` APIs; source overrides are not guessed.

`convertInput()` may be empty or call final `FormComponent.setConvertedInput`
with a literal or a private final input's final `getConvertedInput()`. Such
callbacks do not change component attachment. Other conversions, converters,
model wiring, callbacks, branches, mutable fields, initializer blocks, escapes,
and unknown methods retain uncertainty. A custom `getId()` override or ID
transformation prevents trusting the outer ID contract. This is a supported
subset of custom inputs, not general execution of arbitrary Java.

Plain `FormComponent` implementations that themselves add inline children remain
explicitly unresolved at that child scope. Use a markup-owning composite for
the supported separate-companion analysis.

Constructor tracing is limited to 12 levels, 24 source files, and 256 constructor
visits per trace. Consulted Java contracts participate in snapshot freshness.
Reports remain partial; real application evaluation is deferred.

## Demo

Open `example.FormComponentsPage`: expect **3 MATCHED** findings (`form`, `name`,
`editor`), with `preview` inactive. Open `example.CompositeInput` or its HTML:
expect **1 MATCHED** internal `value` field. `CustomInput` demonstrates a direct
`FormComponent` leaf, and `CompositeInput` demonstrates a private final input
and value conversion. These are static fixtures, without running a web server.

`WicketFormComponentsTest` and `WicketFormComponentsEditorTest` contribute 26
regressions; the full 481-test suite passes. The demo compiles twelve source
classes. Packaging, plugin structure/configuration, and binary compatibility
verification pass against the pinned IntelliJ version, with the existing four
deprecated and six experimental API notices.

The graphical sandbox confirms three parent matches and one separate internal
match, automatic following when opening the composite class, outer-node
navigation to the page HTML, and root navigation to the composite HTML.
